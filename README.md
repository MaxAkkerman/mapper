# Визуальный маппер данных (form state → request body)

React-компонент для low-code платформы: визуально связывает поля источника
(например, состояние формы) с полями тела запроса — drag-and-drop или
клик-клик, без ручного написания кода трансформации.

Демо: `npm install && npm run dev`, см. `src/App.tsx` — там же полный пример
использования `<DataMapper>` с формой заказа (адрес, корзина товаров, пустой
свободный объект `meta`).

## 1. Что нужно было решить

Исходные требования:

1. Визуальный D&D / связывание линиями.
2. Прямая связь: одна переменная → одна.
3. Много переменных → одна (`formState.name` + `formState.city` → `payload.fio`).
4. Раскрытие вложенного объекта и перекладка его полей в переменные тела запроса.
5. Работа с массивами — видно, что это цикл/перебор, и какие вложенные поля доступны внутри.
6. Кастомные обработчики преобразования полей.
7. Итог — JSON.
8. Тип переменной определяет доступные обработчики.
9. Максимально интуитивно, минимум кликов.

Затем добавились три уточняющих требования (см. §6 и §5.1):

10. Объект в теле запроса может быть пустым (например `payload`/`meta`) —
    нужно переносить в него любые поля источника и удалять их.
11. Любое поле тела запроса может быть опциональным — нужна возможность
    создавать поля разных типов вручную в обоих столбцах.
12. Массив по умолчанию переносится как есть; редактирование по элементам —
    только после явного «Открыть перебор».

Затем — ещё два (см. §6.1):

13. Возможность передать в `DataMapper` дополнительный **контекст**
    (произвольный объект со значениями) — с редактируемой JSON-вкладкой
    «Контекст» в самом компоненте.
14. Автодополнение по имени при создании нового поля **в левом столбце**:
    подсказки из `context` и из полей `source`, которых сейчас нет в дереве
    (например, были удалены вручную). Правый столбец (тело запроса) эта
    фича не затрагивает.
15. Сортировка полей в обоих столбцах: сначала связанные (есть стрелка к
    полю с другой стороны), затем остальные — чтобы стрелки не пересекались
    и связи читались линейно (см. §2.1).
16. Вкладка «Состояние формы» — JSON-редактор примера `source` прямо в
    компоненте, с проверкой на blur: невалидный JSON не применяется к
    маппингу (см. §3.4).

Ниже — как каждое требование отражено в архитектуре, какие решения были
приняты и почему, и что осталось как зона роста.

## 2. Ключевое архитектурное решение: гибрид D&D + клик

Выбор стоял между тремя визуальными моделями (граф со стрелками a-la
n8n/Zapier, чистый drag&drop в поле ввода, гибрид). Взят **гибрид**:

- поля источника и цели показаны как два дерева рядом;
- связь создаётся перетаскиванием (`pointerdown` → `pointermove` → `pointerup`,
  кастомная реализация на Pointer Events, не HTML5 DnD — это даёт «резиновую
  линию», которая тянется за курсором, и точный drop по `elementFromPoint`);
- альтернативно — режим «клик-клик»: клик по полю источника, клик по полю
  цели. Переключается тумблером в тулбаре. Это даёт вариант с минимальным
  риском промаха (актуально для маленьких целевых элементов) и работает без
  мыши с точным позиционированием;
- связи рисуются SVG-кривыми Безье поверх обоих деревьев, с подсветкой при
  наведении на любой из концов связи.

**Почему не чистый граф-редактор (React Flow):** для мапинга полей типична
ситуация «один объект слева, один объект справа», а не произвольная сеть
узлов. Графовый UI для этого избыточен (лишняя свобода перемещения узлов,
больше кликов на прокладку связи) и хуже читается при большом количестве
полей — реестр полей нужно проматывать как список, а не искать на холсте.

### 2.1. Сортировка: связанные поля сверху, с точным парным выравниванием

Список полей — не статичный порядок из примера, а живой: в обоих столбцах,
на **любом уровне вложенности** (корень дерева и внутри каждого объекта
отдельно), поля со связью группируются наверх, остальные — под тонким
пунктирным разделителем ниже (`partitionByConnection()` в `treeUtils.ts`).

Внутри группы связанных полей порядок — не исходный порядок из примера, а
**порядок создания связей**, одинаковый для обоих столбцов: N-я по счёту
связь занимает N-ю строку сверху **на обеих сторонах одновременно**. Для
обычной связи «одно поле → одно поле» это даёт точное построчное совпадение:
строка источника и строка цели оказываются на одной высоте, линия между ними
почти горизонтальна и не пересекается с соседними. Порядок связей — это
позиция мапинга в `mappingsAtScope` (та же последовательность, в которой
конфиг мапинга сериализуется в JSON), а не позиция поля в дереве — поэтому
связать поля можно в любом порядке (не сверху вниз) и они всё равно встанут
друг напротив друга.

`connectionOrderKey()` в `treeUtils.ts` даёт каждому полю пару
`[индекс мапинга, индекс источника внутри мапинга]`:

- для **цели** — индекс мапинга, у которого `targetPath` совпадает с полем
  или указывает на что-то внутри него (для контейнера без собственной связи,
  но со связанным потомком — см. ниже);
- для **источника** — минимальный индекс среди всех мапингов, где путь поля
  встречается в `sources` (одно и то же поле-источник можно подключить сразу
  к нескольким целям — тогда оно встаёт по самой ранней из связей), и внутри
  этого мапинга — позиция среди перечисленных источников (второй, третий
  источник многие-к-одному идёт следующей строкой сразу за первым).

Как и раньше, связь засчитывается не только по точному совпадению пути, но
и через потомка: объект без собственного мапинга, но со связанным вложенным
полем, тоже входит в отсортированную группу — на позиции своей самой ранней
внутренней связи, иначе контейнер обгонял бы своё же содержимое или отставал
от него.

Что это даёт на практике (см. §12 — воспроизведено вручную): связали
`isSubscribed→isActive`, затем `city→location` не по порядку схемы (пропустив
`name`/`lastName`/`age`/`birthDate`) — оба поля сразу встали строками 0 и 1 в
обоих столбцах, без единого пересечения линий. Для мульти-источника
(`name`+`lastName` → `fullName`) оба источника встают подряд (в порядке
подключения), сразу над/под остальными независимыми связями, а не
вперемешку с ними — веер линий к одной цели не задевает соседние прямые
связи.

**Честно об ограничении:** это не решение задачи минимизации пересечений
линий в общем виде (она NP-трудна для произвольного двудольного графа) — это
жадный, но точный для реальных сценариев порядок: строгое совпадение позиций
гарантировано для связей «один-к-одному», для «многие-к-одному» источники
аккуратно группируются вокруг своей цели. Если между двумя независимыми
связями пересечение всё-таки нужно (например, X₁→Y₂ и X₂→Y₁ при любом
порядке дают пересекающиеся линии), эта сортировка его не уберёт — но такой
случай означает противоречащий друг другу порядок связей, а не недоработку
alignment-алгоритма.

Порядок реагирует на изменения мгновенно: как только поле связывается, оно
переезжает в верхнюю группу на следующий кадр.

## 3. Модель данных

### 3.1. Схема (откуда берутся поля)

Схема строится не декларативно, а **интроспекцией примера данных**
(`src/lib/introspect.ts`): компонент принимает `source`/`target` как обычные
JS-объекты (то самое `formState` и шаблон `payload`), сам определяет типы и
строит дерево `SchemaNode`:

```ts
interface SchemaNode {
  path: string;       // "customer.fullName", "items[].sku"
  key: string;
  type: 'string' | 'number' | 'boolean' | 'date' | 'object' | 'array' | 'null' | 'any';
  children?: SchemaNode[];  // для object
  itemNode?: SchemaNode;    // форма одного элемента — для array
  sample?: unknown;         // пример значения, для превью в попапе обработчика
  custom?: boolean;         // поле добавлено вручную в UI, а не из примера — см. §6
}
```

Это было решено осознанно в пользу «работаем с реальными данными платформы»
вместо отдельного языка описания схемы (JSON Schema и т.п.) — на low-code
платформе `formState` и шаблон запроса и так существуют как обычные объекты
рантайма, дублировать их описание отдельной схемой означало бы рассинхрон.
Обратная сторона: тип поля с примером `null` определяется как `null`/`any` —
для таких полей стоит передавать пример с реальным значением, чтобы обработчики
фильтровались по осмысленному типу (см. §9, «Известные ограничения»).

Поверх интроспектированного дерева накладываются **пользовательские правки**
(добавленные/удалённые вручную поля, §6) — чистой функцией `applyEdits()` в
`src/lib/schemaEdits.ts`, не мутируя исходное дерево. Это значит, что
`source`/`target` остаются пропсами, которые компонент только читает: правки
живут в собственном состоянии компонента и не требуют от платформы ничего
менять в переданных примерах.

### 3.2. Массивы и путь `items[]`

Путь **самого поля-массива** не содержит `[]` (`"items"`), а путь **формы
одного элемента** — содержит (`"items[]"`, вложенные поля — `"items[].sku"`).
Это разделение — суть решения по массивам (см. §5).

### 3.3. Конфигурация маппинга

```ts
interface FieldMapping {
  id: string;
  targetPath: string;      // "customer.fullName" или "items" (для loop)
  kind: 'value' | 'loop';
  sources: { path: string }[];   // >1 элемент = много-к-одному
  transform?: TransformSpec;     // identity | builtin | custom | inline
  children?: FieldMapping[];     // для loop: маппинги внутри элемента массива —
                                   // пусто = массив копируется как есть, см. §5.1
}
```

Это дерево — самостоятельный сериализуемый JSON (`{ version: 1, mappings }`),
который платформа хранит и позже применяет через `applyMapping(source, mappings, customHandlers)`
без UI (чистая функция, `src/lib/applyMapping.ts`). Компонент отдаёт его через
`onChange`.

### 3.4. Редактирование `source` вживую: вкладка «Состояние формы»

Проп `source` — это только *исходное* значение. Внутри компонента им
инициализируется отдельное состояние (`effectiveSource`) — от него, а не
от пропа напрямую, строится схема (`rawSourceRoot`) и считается
`applyMapping(effectiveSource, ...)` для «Результат (JSON)». Тот же приём,
что и для `mappings`/`initialMapping` и для `context` (§6.1): проп только
сеет стартовое значение, дальше редактор в UI живёт своей жизнью.

Вкладка «Состояние формы» (название берётся из пропа `sourceLabel` — то же,
что заголовок левого дерева, так они всегда согласованы) — текстовый
JSON-редактор поверх `effectiveSource`. Правки применяются **не на каждое
нажатие клавиши, а по `onBlur`** — так и было явно запрошено, чтобы
промежуточные ошибочные состояния при наборе не дёргали схему и результат
на каждый символ:

- при потере фокуса поля текст пытаются распарсить (`JSON.parse`);
- если валидно — именно этот объект становится новым `effectiveSource`
  (схема слева и «Результат» сразу пересчитываются), а текст в поле
  форматируется заново (`JSON.stringify(..., null, 2)`) для аккуратности;
- если невалидно — **`effectiveSource` не трогается вообще**: ни схема, ни
  результат не меняются, ничего не «применяется в DataMapper», как и
  просили. Поле редактора при этом подсвечивается (красный фон) и под ним
  показывается сообщение об ошибке `JSON.parse` — текст, который набрал
  пользователь, никуда не пропадает и не откатывается, чтобы можно было
  дописать/поправить и уйти с поля ещё раз.

Живая (посимвольная) проверка тоже есть — она только для отображения
ошибки под полем по мере набора, отдельно от логики применения на blur;
`sourceTextError` в `JsonPreviewPanel.tsx` пересчитывается на каждое
изменение текста, а коммит в `effectiveSource` — только из `onBlur`.

**Не в области этой задачи, но стоит знать:** правка `source` меняет форму
и/или типы полей дерева, а существующие связи (`mappings`) при этом **не
чистятся** — путь, который пропал из нового JSON, просто перестаёт что-то
находить (`getByPath` возвращает `undefined`) в `applyMapping`, без падения,
но и без предупреждения в UI. Это осознанно не совмещено с автоочисткой,
которая уже есть для 🗑 (§6) — там пользователь явно удаляет поле, здесь же
правка JSON могла быть опечаткой, и молча удалять чьи-то связи из-за неё
рискованнее, чем оставить их немного протухшими.

## 4. Прямая связь и «много-к-одному»

- Первое перетаскивание/клик на пустое целевое поле создаёт `sources: [one]`,
  `transform` не задан (значит «как есть», identity).
- Перетаскивание **второго** источника на уже занятое целевое поле **не
  заменяет**, а добавляет в `sources` — ровно тот кейс из требования
  (`formState.name`, `formState.city` → один `payload.fio`). В момент, когда
  источников становится больше одного, автоматически подставляется
  обработчик `concat` (склейка через пробел) — так поле никогда не остаётся
  в невалидном «непонятно что показывать» состоянии, а пользователь сразу
  видит результат и может тут же сменить обработчик на «Шаблон строки» или
  кастомный.
- У каждого источника в целевом поле — отдельный чип с крестиком: можно
  убрать один из нескольких источников, не трогая остальные.

## 5. Массивы: цикл, а не редактирование по элементам

Требование — «видно, что это цикл, и какие вложенные поля доступны». Решение:

1. Поле-массив в обоих деревьях **не разворачивается инлайн** в список
   элементов. Вместо этого строка показывает бейдж `🔁 for each` и краткую
   сводку полей элемента (`sku, title, price, qty`) — читается сразу, без
   клика.
2. Массив связывается с массивом **целиком** (перетаскивание/клик, как
   обычное поле) — это создаёт `FieldMapping.kind === 'loop'`.
3. После этого у целевого поля появляется кнопка **«Открыть перебор →»** —
   она переключает оба дерева в **скоуп одного элемента массива**: слева и
   справа теперь показана форма одного элемента (`sku/title/price/qty` →
   `code/name/unitPrice/total`), с точно тем же интерфейсом связывания,
   рекурсивно (в т.ч. вложенные массивы внутри элемента — тот же механизм
   на любую глубину). Хлебные крошки сверху (`Корень / 🔁 items`) возвращают
   на уровень выше в один клик.

Почему не «раскрыть массив прямо в дереве»: элементов массива в реальных
данных может быть много и с разными по факту полями (опциональные ключи),
инлайн-раскрытие сразу создаёт вопрос «мы редактируем элемент №0 или
шаблон для всех?». Отдельный экран-скоуп для «одного элемента» убирает эту
двусмысленность визуально: пользователь физически не может связать поле
внутри массива с полем вне цикла.

### 5.1. По умолчанию — как есть, перебор только по явному действию

Изначально соединение массив↔массив уже создаёт `FieldMapping.kind: 'loop'`,
но **без единого дочернего маппинга**. `applyMapping()` трактует loop-маппинг
с пустым `children` как **прямое копирование массива как есть**
(`sourceArray.slice()`) — а не как «массив пустых объектов», как было бы при
наивной реализации «применить 0 дочерних правил к каждому элементу».

Только когда пользователь заходит через «Открыть перебор →» и связывает
внутри хотя бы одно поле, `children` перестаёт быть пустым, и с этого момента
`applyMapping()` вместо копирования **вычисляет каждый элемент** из заданных
внутри правил (только перечисленные поля, остальные в исходном элементе
игнорируются — это осознанный переход в «точечный» режим, а не слияние двух
разных стратегий на одном массиве).

Строка массива в дереве цели явно показывает текущий режим бейджем рядом с
кнопкой:

- `= как есть` — маппингов внутри ещё нет, копируется исходный массив целиком;
- `✎ N полей` — перебор уже настроен, элементы вычисляются по правилам.

Удаление последнего дочернего маппинга внутри перебора (через 🗑, см. §6)
автоматически возвращает массив в режим «как есть» — не оставляет его
«наполовину настроенным» с пустым результатом.

## 6. Свободные и опциональные поля: добавление/удаление вручную

Исходная интроспекция фиксирует набор полей примером данных. Для двух
сценариев этого недостаточно: (а) тело запроса содержит объект, чья форма
заранее не известна (`payload`/`meta: {}` в демо) — его поля появляются по
мере разработки интеграции; (б) любое поле, включая пришедшее из примера,
может быть **необязательным** для конкретного сценария и его нужно убрать из
маппинга, не трогая исходные `source`/`target`.

Решение — редактируемый слой поверх интроспектированной схемы
(`addedFields`/`removedPaths` в состоянии `DataMapper`, применяется через
`applyEdits()`, см. §3.1), с тремя точками входа в UI:

1. **Перетаскивание/клик на строку объекта** (не на конкретное дочернее
   поле) — если у объекта ещё нет поля с таким именем, создаётся новое поле
   того же типа, что и источник, и сразу связывается. Работает для пустых
   объектов (`meta` в демо) и для объектов с уже заданной формой — так же
   можно докинуть поле, которого не было в примере. Если поле с таким именем
   уже есть — переиспользуется оно, а не плодится дубликат.
2. **«+ Добавить поле»** — под списком полей любого объекта (в т.ч. в корне
   каждого дерева) в обоих столбцах. Открывает инлайн-форму: имя + тип
   (`string/number/boolean/date/object/array`) → «Добавить». Не требует
   предварительного соединения — так проверяется требование «создавать
   разные типы полей в обоих столбцах» независимо от того, есть ли уже
   что связывать. Добавленное поле типа `object`/`array` само становится
   «открытым» (пустые `children`/`itemNode`) — в него так же можно добавлять
   поля рекурсивно, и с массивом работает то же правило «как есть по
   умолчанию» из §5.1.
3. **🗑 на любой строке** (обеих сторон, и у полей из примера, и у добавленных
   вручную) — убирает поле из схемы для этой сессии редактирования. Каскадно
   подчищает маппинги: если удалено целевое поле (или предок с вложенными
   полями) — падает весь связанный с ним маппинг и его `children`; если
   удалено поле-источник — оно вычищается из `sources` (а если это был
   единственный источник или это была ссылка на массив, который перебирали —
   падает весь маппинг). Если пользователь в этот момент был внутри
   «перебора» этого массива — сессия возвращает его в корень, а не оставляет
   в несуществующем скоупе.

Добавленные вручную поля помечены бейджем `доб.` — это просто визуальная
подсказка «этого не было в примере», не влияет на поведение.

**Важный нюанс для интеграции:** поле, добавленное на стороне **источника**
вручную, в демо-превью не имеет значения (в переданном `source`-примере
такого ключа нет, поэтому в JSON-превью оно молча пропадёт — `JSON.stringify`
опускает `undefined`). В реальном использовании оно должно соответствовать
полю, которое **действительно существует** в объекте, приходящем в
`applyMapping()` в проде (например, платформа передаёт для превью урезанный
пример, а в реальном `formState` поле есть) — это осознанное разделение
«из чего строится список полей для UI» и «что реально прилетит в рантайме»,
а не баг.

### 6.1. Контекст и автодополнение при добавлении поля

`context?: unknown` — ещё один проп, рядом с `source`/`target`: произвольный
объект дополнительных значений (сессионные/платформенные переменные и т.п.),
которые не показываются как отдельное дерево, но полезны при создании нового
поля в источнике вручную.

**Вкладка «Контекст»** — третья вкладка в панели превью, справа от «Конфиг
маппинга» (`JsonPreviewPanel.tsx`). Это текстовый **JSON-редактор**, а не
просто просмотр: он инициализируется значением пропа `context` (аналогично
тому, как `initialMapping` только *сеет* внутреннее состояние `mappings`, а
дальше живёт своей жизнью в UI) и редактируется прямо в компоненте — так
можно попробовать разные наборы контекстных значений, не трогая код
интеграции. Невалидный JSON не роняет компонент: под полем показывается
ошибка парсинга, а до её исправления автодополнение просто не предлагает
значений из контекста (`{}` как безопасный фолбэк).

**Автодополнение** — только в «+ Добавить поле» **источника** (левый
столбец; на правом столбце, как и просили, ничего не менялось). При наборе
имени поля выпадает список подсказок с типом (`getSourceFieldSuggestions()`
в `DataMapper.tsx`), собранный из двух источников:

1. Поля `source`, которых сейчас **нет среди живых детей того же родителя**
   в (уже отредактированном) дереве — типичный кейс: пользователь удалил
   поле через 🗑, а потом захотел добавить его обратно. Сравнение идёт по
   тому же `parentPath`, где открыта форма, — то есть вложенное «+ Добавить
   поле» внутри `address` предложит поля, удалённые именно из `address`, а
   не вообще откуда угодно из `source`.
2. Верхнеуровневые ключи `context` (текущее, отредактированное в вкладке
   значение) — они предлагаются **на любом уровне вложенности** (контекст не
   привязан к структуре `source`, это плоский набор «доступных значений»),
   за вычетом ключей, уже присутствующих как живой ребёнок в этой конкретной
   точке дерева.

Тип для подсказки берётся из реального значения (`detectType()`,
переиспользует ту же логику, что и интроспекция схемы) — выбор подсказки
сразу подставляет и имя, и тип в форму, их всё ещё можно поправить вручную
перед «Добавить».

Технически список рендерится через `createPortal` в `document.body` с
позицией, посчитанной от `getBoundingClientRect()` инпута (`AddFieldForm.tsx`):
дерево полей скроллится (`overflow-y-auto`), и обычный `position: absolute`
внутри него подсказки бы обрезал — портал выносит их за пределы любого
клип-контейнера.

## 7. Кастомные обработчики и типизация

Три уровня обработки значения перед записью в целевое поле
(`TransformSpec`, `src/lib/handlers.ts`, `src/lib/applyMapping.ts`):

1. **Встроенные** (`BUILTIN_HANDLERS`) — 16 штук на все базовые типы:
   `upperCase/lowerCase/trim`, `concat/template` (много-к-одному),
   `toNumber/round/multiply`, `toBoolean/negate/yesNo`,
   `formatDate/toISOString`, `join/length` для массивов и т.д.
2. **Кастомные, зарегистрированные платформой** (`customHandlers` проп,
   массив `CustomHandlerDef` с обычной JS-функцией `run(values)`) — это
   основной сценарий добавления бизнес-специфичных обработчиков
   (`priceWithVat`, `lineTotal = price × qty` — см. `src/demo/customHandlers.ts`).
   Не требует `eval`, платформа просто передаёт функции как проп.
3. **Инлайн-код** («✎ Написать свой JS-обработчик» в попапе преобразования) —
   для одноразовых случаев прямо в UI, выполняется через `new Function('values', code)`.
   **Осознанный компромисс**: это `eval`-подобный механизм. Он оставлен, потому
   что того требует UX «быстро попробовать формулу не выходя из редактора»,
   но выполняется только над **локальными данными примера** внутри
   визуального редактора конфигурации, а не в проде на реальных пользовательских
   данных бесконтрольно — итоговое применение (`applyMapping`) платформа
   вызывает сама и может на своей стороне решить не пропускать `kind: 'inline'`
   в продакшен-исполнение (запретить сериализацию таких мапингов), если нужна
   более строгая модель безопасности. Это explicit hook, а не скрытое поведение.

**Фильтрация по типу** — каждый обработчик описывает `appliesTo: FieldType[]`
и `minSources/maxSources`. Попап преобразования (`TransformPopover.tsx`)
вычисляет типы **подключённых источников** и показывает только применимые
обработчики (builtin и кастомные) — ровно требование «в соответствии с типом
выводить доступные обработчики». У каждого обработчика в списке — живое
превью результата на примере данных, посчитанное тут же, без применения.

## 8. Минимум кликов — конкретные решения

- **Авто-связывание** (кнопка «✨ Авто-связать»): одним кликом связывает все
  пары полей с одинаковым именем (без учёта регистра) и совпадающим
  «это массив или нет» на текущем уровне (корень или внутри цикла). В демо
  типовая форма связывается почти полностью одним кликом (`age` находится
  само; `sku/title/price` — после захода в цикл).
- **Поиск по полю** в каждом дереве — с автораскрытием совпадающих веток,
  без ручного разворачивания глубоко вложенных объектов.
- **Липкий источник в режиме «клик-клик»**: после клика по источнику
  выделение остаётся, пока не кликнули по цели или по другому источнику —
  можно быстро связать один и тот же источник с несколькими целями подряд.
- Счётчик на свёрнутом объекте (`{N}` рядом с типом) показывает, сколько
  полей внутри уже связано — не нужно разворачивать «просто проверить».
- Связь можно провести **в объект целиком** (не только в листовые поля) —
  для объекта с предопределённой формой это создаёт новое поле-обёртку по
  имени источника (см. §6, п. 1), сохраняя за пользователем возможность
  точечно переопределить конкретные поля внутри отдельными связями —
  `applyMapping` корректно склеивает оба уровня (более специфичный путь,
  применённый позже, точечно переопределяет поле внутри уже скопированного
  объекта, не переписывая остальные поля — реализовано через `setByPath`,
  который идёт по сегментам пути и не затирает соседние ключи).

## 9. Известные ограничения / зоны роста

- **Инлайн `kind: 'inline'` обработчики** используют `new Function` — см. §7,
  сознательный компромисс, а не недосмотр.
- Тип поля с примером `null`/пустым массивом определяется как `null`/`any` —
  стоит передавать в `source`/`target` примеры с непустыми репрезентативными
  значениями (в т.ч. непустой массив с одним элементом), чтобы типизация и
  фильтрация обработчиков были осмысленными.
- Массивы вложенных массивов поддержаны архитектурно (рекурсивный скоуп,
  `scopeChain: string[]` — сколько угодно уровней), но не покрыты ручным
  тестированием на глубину >1 — при выходе за пределы демо-кейса стоит
  дополнительно проверить.
- Нет отмены/истории изменений (undo/redo) — конфиг можно только строить
  вперёд или чистить целиком/по уровню («Очистить всё» — очищает текущий
  скоуп, не всё дерево). Добавленные/удалённые вручную поля (§6) тоже живут
  только в состоянии сессии редактирования — платформе, если нужно
  восстанавливать их между сессиями, стоит сохранять их отдельно от
  `mappings` (сейчас через `onChange` уходит только сам маппинг, не список
  ручных правок схемы) либо просто держать актуальный пример `target` вместе
  с уже добавленными в него полями.
- При удалении поля (🗑) подтверждения не запрашивается — сделано осознанно
  ради минимума кликов (действие легко обратимо через «+ Добавить поле» с тем
  же именем), но если у поля уже настроен сложный кастомный трансформ с
  несколькими источниками, его придётся собрать заново.
- Автодополнение из `context` (§6.1) берёт только **верхнеуровневые** ключи —
  вложенные значения (`context.user.id`) не разворачиваются в отдельные
  подсказки; при выборе такого ключа новое поле создаётся с типом `object` и
  пустыми `children`, дальше его можно донаполнить вручную через «+ Добавить
  поле» внутри него же.
- `context`, как и `initialMapping`, читается только при монтировании — сам
  редактор JSON-вкладки после этого живёт своей жизнью в состоянии
  компонента; если платформе нужно узнать текущее (отредактированное в UI)
  значение контекста снаружи, для этого сейчас нет отдельного колбэка (по
  аналогии с `onChange` для маппинга) — не было в требованиях, но следующий
  логичный шаг, если появится сценарий «сохранить и контекст тоже».
- Правка `source` через вкладку «Состояние формы» (§3.4) не чистит `mappings`
  за собой: если поле, на которое уже есть связь, пропадает из нового JSON,
  связь остаётся, просто перестаёт что-то находить (тихо, без падения) — по
  той же причине, что и выше: колбэка «применили новый source» наружу нет,
  только `onChange` по маппингу.

## 11. Публичный API компонента

```tsx
<DataMapper
  source={formStateExample}         // пример состояния формы
  target={payloadTemplate}          // пример/шаблон тела запроса (может включать пустые {})
  context={contextExample}          // опционально — доп. значения для автодополнения, см. §6.1
  customHandlers={demoCustomHandlers}
  sourceLabel="Состояние формы"
  targetLabel="Тело запроса (payload)"
  initialMapping={savedMapping}     // опционально — восстановить сохранённый конфиг
  onChange={(config) => save(config)}  // { version: 1, mappings: FieldMapping[] }
/>
```

Применение сохранённого конфига в рантайме платформы (без UI):

```ts
import { applyMapping } from './components/DataMapper';

const payload = applyMapping(actualFormState, savedConfig.mappings, customHandlersMap);
```

## 12. Проверено вручную (браузер)

- Drag-and-drop связывание и режим «клик-клик» — оба пути работают на всех
  сценариях ниже.
- Много-к-одному (`name + city → fullName`) с авто-подстановкой `concat`,
  сменой на `template` и на кастомный обработчик `initials` — превью и
  итоговый JSON совпадают.
- Массив `cart → items`: связывание массива целиком **без захода в перебор**
  корректно копирует его как есть (`= как есть`, полный JSON элементов в
  выводе); заход в перебор и связывание `sku→code`, `title→name`,
  `price→unitPrice`, `price+qty→total` (кастомный `lineTotal`) переключает
  бейдж на `✎ N полей` и пересчитывает элементы по правилам
  (`total: 4990` и `total: 3980` для двух товаров).
- Пустой объект `meta`: перетаскивание `isSubscribed` создаёт поле
  `meta.isSubscribed` и сразу связывает его; ручное «+ Добавить поле»
  (`discountCode: string`) в дереве источника и последующая связка с `meta` —
  оба пути подтверждены.
- Удаление поля (🗑): убирает поле и связанный с ним маппинг; удаление
  единственного дочернего маппинга внутри перебора возвращает массив в режим
  «как есть»; удаление всего поля-массива убирает маппинг целиком и сбрасывает
  открытый скоуп перебора обратно в корень.
- Авто-связывание по имени поля (`age→age`).
- Возврат по хлебным крошкам в корень с сохранением ранее созданных связей.
- Вкладка «Контекст»: редактируется, невалидный JSON не ломает компонент.
  Автодополнение в «+ Добавить поле» источника после удаления `birthDate`
  показывает его снова (тип `string`, подхвачен из исходной схемы) вместе с
  ключами контекста (`sessionId`, `locale` — `string`; `isTestOrder` —
  `boolean`, тип определён автоматически по значению); фильтрация по вводу и
  выбор подсказки (имя + тип) работают; на вложенном уровне (внутри
  `address`) предлагаются только ключи контекста — `birthDate`, удалённый из
  корня, там не показывается (подсказки из `source` привязаны к тому же
  `parentPath`, что и открытая форма).
- Сортировка и парное выравнивание (§2.1): связали `isSubscribed→isActive`,
  затем `city→location` — не по порядку схемы (`name`/`lastName`/`age`/
  `birthDate` пропущены) — обе пары встали строго на позиции 0 и 1 **в обоих
  столбцах одновременно** (внутри `customer`), с разделителем под ними и
  без единого пересечения линий. Добавили `name`+`lastName → fullName`
  (многие-к-одному): оба источника встали подряд в порядке подключения,
  веер линий к `fullName` не задел независимые связи выше. Отдельно
  подтверждена сортировка **корневого** уровня: `customer` (мапинги созданы
  раньше) встал выше `meta` (связь добавлена позже), обе — выше ещё не
  тронутых `shipping`/`items`.
- Вкладка «Состояние формы» (§3.4): связали `name → fullName`, поменяли в
  редакторе значение `name` на «Мария» и увели фокус — «Результат (JSON)»
  сразу показал `fullName: "Мария"`. Затем сломали JSON (вставили `broken`
  внутрь) и увели фокус — результат остался прежним (`"Мария"`), схема и
  дерево слева не пострадали, под полем появилось сообщение об ошибке
  `JSON.parse`, набранный (невалидный) текст остался в поле как есть. После
  восстановления валидного JSON поле переформатировалось и подсветка
  ошибки пропала.

В процессе этой проверки были найдены и исправлены три реальных бага:

1. В `applyMapping.ts` поля внутри цикла (`items[].code`) изначально
   резолвились в `target.items.code` вместо `target.code` внутри элемента
   массива — из-за того, что путь самого поля-массива не содержит `[]`, а
   поля внутри элемента содержат. Исправлено передачей явного префикса скоупа
   (`items[].`) при рекурсивном спуске в `applyOne`, см. §3.2 и §5.
2. Кнопка удаления поля, добавленная у правого края строки, сдвигала позицию
   «ручки» для перетаскивания и пробивала уже работавший drag-and-drop —
   перенесена левее, среди прочих бейджей, положение ручки перетаскивания
   (крайний правый элемент строки) больше не меняется от появления других
   контролов.
3. Список подсказок автодополнения изначально рендерился обычным
   `position: absolute` внутри скроллящегося дерева и обрезался его
   `overflow-y-auto` (было видно только 2–3 пикселя списка) — исправлено
   выносом через `createPortal` в `document.body`, см. §6.1.

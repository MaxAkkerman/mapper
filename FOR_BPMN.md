# Доработки маппера под BPMN-движок

Разбор четырёх запросов на доработку: что из этого уже есть в проекте
(по `README.md` и коду в `src/`) и как реализовать недостающее.

Принятые решения:

- **целевой язык маппинга — только Groovy.** JUEL не поддерживаем;
- **адресация источников — только JSONPath** (RFC 9535);
- **отладка реализуется полностью** (UI, трассировка, тест-кейсы, контракт
  исполнителя), но исполнение Groovy **пока замокано**. Реальный
  бэкенд-исполнитель подключается позже без изменений в UI.

Текущее состояние:

| Запрос | Есть сейчас? |
|---|---|
| 1. Маппинг на Groovy | **Нет.** Единственный рантайм — JS (`applyMapping.ts`), инлайн-код — JS через `new Function`. |
| 2. JSONPath вместо dot-нотации | **Нет.** Пути — строки с `.` и маркером `[]`. К полям внутри массивов можно добраться только через «Открыть перебор». |
| 3. Отладка: подать пример входа, получить выход | **Частично.** Вкладка «Состояние формы» + «Результат (JSON)» уже работают как простой отладчик, но у них есть ограничения (см. §3). |
| 4. Подсказки по аргументам функций | **Нет.** Обработчики получают позиционный `values: unknown[]` без описания аргументов. |

Предлагаемый порядок работ: **2 → 4 → 1 → 3**. От формата путей (2) и
сигнатур обработчиков (4) зависит кодогенерация Groovy (1), а отладка (3)
показывает и трассирует именно сгенерированный Groovy.

## 1. Маппинг на Groovy

### Что есть сейчас

- Конфиг маппинга (`MappingConfig`, `{ version: 1, mappings }`) не привязан
  к языку. Это декларативное дерево (`FieldMapping` → `sources`, `transform`,
  `children`), и это хорошо: из него можно генерировать Groovy.
- Исполняет его только JS-функция `applyMapping()`. Встроенные обработчики
  (`BUILTIN_HANDLERS`) и кастомные (`CustomHandlerDef.run`) — JS-функции.
- `TransformSpec { kind: 'inline', code }` — JS-код, который выполняется
  через `new Function('values', code)`.

BPMN-движок (Camunda 7 и совместимые) исполняет маппинги в JVM
(`camunda:inputOutput`, `camunda:script scriptFormat="groovy"`) и
JS-функции из конфига не выполнит. Значит, нужен **компилятор конфига в
Groovy-скрипт**. JS-рантайм остаётся только для мгновенного превью в
редакторе.

### Как реализовать

**1.1. Модель.** Версия конфига поднимается до 2. Язык не выбирается (он
один), поле `language` фиксировано, но оставлено в формате на будущее:

```ts
interface MappingConfig {
  version: 2;
  language: 'groovy';
  mappings: FieldMapping[];
  testCases?: MappingTestCase[];   // см. §3.4
}

type TransformSpec =
  | { kind: 'identity' }
  | { kind: 'builtin'; handlerId: string; params?: Record<string, unknown> }
  | { kind: 'custom'; handlerId: string }
  | { kind: 'inline'; code: string };   // теперь это Groovy, а не JS
```

Миграция `v1 → v2` (`src/lib/migrate.ts`): пути конвертируются в JSONPath
(§2.6). Инлайн-JS-обработчики сохраняются как есть, но помечаются
предупреждением «JS-код — перепишите на Groovy», потому что автоматически
их не перевести. `new Function` из `applyMapping` убирается, и заодно
снимается компромисс из §7 README.

**1.2. Обработчики получают Groovy-шаблон.** Помимо JS-двойника `run` (для
превью) обработчик описывает, как он выглядит в Groovy:

```ts
interface TransformHandler {
  // ...как сейчас
  groovy: (args: Record<string, string>, params: Record<string, unknown>) => string;
}

// пример
{
  id: 'upperCase',
  run: ({ value }) => String(value ?? '').toUpperCase(),
  groovy: ({ value }) => `(${value} ?: '').toString().toUpperCase()`,
}
```

Кастомные обработчики платформы (`CustomHandlerDef`) задают поле `groovy`
одним из двух способов:
- шаблон-строкой, как встроенные;
- ссылкой на Groovy-функцию / Spring-бин, заранее зарегистрированные в
  движке (`mapperFn.priceWithVat(price)`). Для бизнес-логики, которая
  живёт на стороне платформы, это предпочтительнее.

Обработчик без `groovy` в попапе преобразования не показывается (или
показывается неактивным с пояснением). Та же логика, что у фильтра по
типу `appliesTo`.

**1.3. Кодогенератор** — чистая функция `src/lib/codegen/groovy.ts`. Она
обходит дерево `FieldMapping` так же, как `applyOne`. Loop-маппинг
превращается в `collect`, а JSONPath-источники (§2) — в Spin
`jsonPath(...)`:

```groovy
def src = S(formState)
def out = [:]
out.customer = [
  fullName: [src.prop('name').stringValue(), src.prop('lastName').stringValue()]
              .findAll { it }.join(' '),
  age     : src.prop('age').numberValue(),
]
out.items = src.jsonPath('$.cart[*]').elementList().collect { item -> [
  code : item.prop('sku').stringValue(),
  total: item.prop('price').numberValue() * item.prop('qty').numberValue(),
]}
return groovy.json.JsonOutput.toJson(out)
```

Генератор отдаёт также **source map**: диапазон строк скрипта →
`mappingId`. Это нужно отладке (§3.2), чтобы связать ошибку Groovy с
конкретной линией на холсте.

Результат для деплоя — фрагмент BPMN XML:

```xml
<camunda:inputOutput>
  <camunda:inputParameter name="payload">
    <camunda:script scriptFormat="groovy"><![CDATA[ ...сгенерированный код... ]]></camunda:script>
  </camunda:inputParameter>
</camunda:inputOutput>
```

**1.4. UI.** Переключатель языка не нужен. Новая вкладка «Groovy» в
`JsonPreviewPanel.tsx` показывает сгенерированный скрипт и XML-фрагмент
`camunda:inputOutput`, только для чтения, с кнопкой «Копировать».
Редактор инлайн-обработчика в `TransformPopover.tsx` переключается на
Groovy: подсветка синтаксиса и подсказки из §4.4.

**1.5. Превью.** Встроенные и кастомные обработчики в браузере считаются
JS-двойником `run`, мгновенно. Инлайн-Groovy в браузере не выполнить: его
превью и полный прогон идут через исполнителя из §3.3, пока замоканного.

## 2. JSONPath вместо dot-нотации

### Что есть сейчас и в чём проблема

- `SourceRef.path` — строка вида `customer.fullName`, `items[].sku`.
  `getByPath()` делает `path.split('.')` и идёт по ключам.
- Индексов нет: взять `cart[0].price` нельзя.
- Проекции нет: получить массив `cart[*].sku` в одно поле, не заходя в
  перебор, нельзя. Маркер `[]` имеет смысл только внутри loop-скоупа, а
  `applyMapping` его просто вырезает (`stripArrayMarkers`).
- Фильтров нет: «товары с `qty > 1`», «первый адрес с `type == 'home'`».
- Ключи с точкой, пробелом или `[` в имени ломают парсер пути.
- Путь в формате самого маппера не переносится в Groovy, его всё равно
  придётся транслировать.

Замечание верное. Через механизм перебора до полей внутри массивов добраться
можно, но только «элемент → элемент». Вытащить значение из массива в
скалярное поле или отфильтровать массив нельзя.

### Почему JSONPath

- В Camunda 7 он есть «из коробки» через Spin:
  `S(formState).jsonPath('$.cart[0].sku').stringValue()`. В Groovy доступен
  и Jayway JsonPath, в браузере — `jsonpath-plus`. Семантика одна на обеих
  сторонах.
- Это язык **выборки**, а не преобразования. Он решает ровно задачу «как
  адресовать данные» и не пересекается с Groovy.
- Текущие пути переводятся в него механически:
  `customer.fullName` → `$.customer.fullName`, `items[].sku` →
  `$.items[*].sku`.

### Как реализовать

**2.1. Модель источника:**

```ts
interface SourceRef {
  /** JSONPath (RFC 9535). Внутри loop-скоупа — относительно элемента: `@.sku`. */
  path: string;
  /** Как трактовать результат выборки: одно значение или список. */
  cardinality?: 'one' | 'many';
  /** Имя аргумента обработчика, в который подаётся значение — см. §4.2. */
  arg?: string;
}
```

JSONPath всегда возвращает список узлов. Правило: если путь «определённый»
(нет `[*]`, `..`, фильтров), берётся первый элемент (`one`), иначе —
массив (`many`). Тип такого источника для фильтрации обработчиков —
`array` с типом элемента (`array<string>`). Тогда, например, `join` и
`length` сразу применимы к `$.cart[*].title`.

**2.2. Целевые пути** оставить структурными (запись по JSONPath плохо
определена), но хранить как **массив сегментов**, а не строку через точку:
`['customer', 'full.name']`. Это решает экранирование ключей. `setByPath`
принимает сегменты, а генератор Groovy строит из них вложенные map-литералы.

**2.3. Loop-маппинг** получает JSONPath-источник, и фильтр становится
бесплатным: `sources: [{ path: '$.cart[?@.qty > 1]' }]`. Дети внутри
перебора используют относительные пути от `@`. Это заодно убирает хрупкую
логику префиксов `relativize()` / `childSourcePrefix` в `applyMapping.ts`,
где уже был баг №1 из §12 README.

**2.4. UI:**

- D&D и клик-клик по-прежнему генерируют путь автоматически. Пользователь
  не обязан знать JSONPath.
- Поле внутри массива в левом дереве теперь можно тащить **и вне
  перебора**. Получится проекция `$.cart[*].price` (бейдж `[*]` на чипе
  источника).
- Чип источника в целевом поле редактируется: по клику открывается поле
  JSONPath с автодополнением из `SchemaNode` (ключи текущего уровня,
  `[*]`, `[0]`, шаблон фильтра `[?@.field == ...]`) и живым превью
  значения на примере данных.
- Невалидный путь не применяется, по аналогии с blur-валидацией JSON в
  «Состоянии формы».

**2.5. Кодогенерация** (связь с §1): простые пути транслируются в цепочку
`prop('...')` Spin (или нативную навигацию по map после `JsonSlurper`), а
проекции и фильтры — в `src.jsonPath('...').elementList()`.

**2.6. Миграция конфигов v1:** автоматическая конвертация строк путей при
чтении `initialMapping`.

## 3. Отладка: пример входа → вариант выхода

### Что уже есть

Базовый сценарий уже работает:

- вкладка «Состояние формы» — JSON-редактор примера `source`, применяется
  на blur (§3.4 README);
- вкладка «Результат (JSON)» — `applyMapping(effectiveSource, mappings)`,
  пересчитывается сразу;
- в попапе преобразования — живое превью каждого обработчика на
  `sample` источников.

То есть «подсунуть вход и получить выход» уже можно. Для BPMN этого
недостаточно:

1. **Пример входа = схема.** Правка «Состояния формы» перестраивает левое
   дерево. Нельзя проверить маппинг на «плохих» данных (пустой массив,
   `null`, отсутствующее поле), не сломав при этом схему и типы.
2. **Исполняется JS, а не Groovy.** Результат в браузере — только
   приближение к тому, что посчитает движок.
3. **Нет трассировки.** Ошибка превращается в строку `#ERROR: ...` в
   выходном JSON. Не видно, какой маппинг что выдал и какие значения
   пришли на вход обработчику.
4. **Нет сохраняемых кейсов.** Проверку нельзя повторить после изменения
   маппинга.
5. `context` в `applyMapping` не передаётся вообще, хотя в BPMN маппинги
   обычно ссылаются на переменные процесса.

### Как реализовать

Отладка делается полностью: UI, трассировка, тест-кейсы и контракт
исполнителя. Замокано только одно место — реализация `GroovyExecutor`
(§3.3).

**3.1. Вкладка «Отладка»** в `JsonPreviewPanel.tsx`, независимая от
примера, по которому строится схема:

- поле «Вход» (JSON) с кнопкой «Взять из примера»;
- поле «Переменные процесса» (JSON, по умолчанию — текущий `context`);
- кнопка **«Выполнить»**, а не пересчёт на каждый ввод: исполнитель
  асинхронный, в будущем это сетевой вызов;
- «Выход» + опциональное «Ожидаемый выход» с diff-подсветкой;
- плашка источника результата: **`Groovy (mock)`** сейчас, `Groovy
  (engine)` после подключения бэкенда. Пользователь не должен принять
  мок за настоящее исполнение.

**3.2. Трассировка.** Единый формат результата для любого исполнителя:

```ts
interface TraceEntry {
  mappingId: string;
  targetPath: string[];
  inputs: Record<string, unknown>;  // значения аргументов после JSONPath-выборки
  output?: unknown;                 // после transform
  error?: string;
  iteration?: number;               // индекс элемента для loop children
  scriptLines?: [number, number];   // диапазон строк в сгенерированном Groovy (source map, §1.3)
}

interface EvaluateResult {
  output?: unknown;
  trace: TraceEntry[];
  error?: { message: string; line?: number; mappingId?: string };
  engine: 'mock' | 'groovy';
  durationMs: number;
}
```

В UI трассировка показывается списком под выходом. Клик по записи
подсвечивает связь в `ConnectionsLayer` и соответствующие строки на
вкладке «Groovy», а также открывает попап связи. Упавшие связи красные
прямо на холсте. Для перебора — переключатель номера итерации.

`applyMapping` получает необязательные `context` и `onTrace`, чтобы
JS-рантайм тоже умел трассировать (на нём построен мок):

```ts
applyMapping(source, mappings, customHandlers, { context, onTrace })
```

**3.3. Исполнитель Groovy: контракт + мок.**

```ts
interface EvaluateRequest {
  script: string;                 // сгенерированный Groovy (§1.3)
  sourceMap: ScriptSourceMap;
  config: MappingConfig;          // для мока и для трассировки на сервере
  input: unknown;
  variables: Record<string, unknown>;
}

interface GroovyExecutor {
  evaluate(req: EvaluateRequest, signal?: AbortSignal): Promise<EvaluateResult>;
}
```

Исполнитель передаётся в компонент пропом:
`<DataMapper groovyExecutor={...} />`. По умолчанию используется
`MockGroovyExecutor` (`src/lib/executors/mockGroovy.ts`):

- исполняет **конфиг**, а не текст скрипта: вызывает
  `applyMapping(input, config.mappings, customHandlers, { context:
  variables, onTrace })`. Генератор Groovy строится по той же семантике,
  поэтому для встроенных и кастомных обработчиков результат мока совпадает
  с ожидаемым результатом движка;
- **инлайн-Groovy не исполняет**: в выход пишется `null`, а в трассировку —
  запись с `error: 'Инлайн-Groovy не исполняется в mock-режиме'` (жёлтая,
  не красная). Остальные связи считаются как обычно;
- добавляет искусственную задержку ~200–400 мс, чтобы UI сразу
  отрабатывал состояния загрузки и отмены (`AbortSignal`), как с настоящим
  сетевым вызовом;
- возвращает `engine: 'mock'`, отсюда плашка в UI (§3.1).

Позже подключается `HttpGroovyExecutor` → `POST /api/mapper/evaluate` с
тем же `EvaluateRequest` / `EvaluateResult`. На стороне платформы это
`GroovyShell` с `SecureASTCustomizer`, таймаутом и Camunda Spin в
classpath тех же версий, что в движке. UI и формат трассировки при этом не
меняются.

**3.4. Тест-кейсы** хранятся в конфиге:

```ts
interface MappingTestCase {
  id: string;
  name: string;
  input: unknown;
  variables?: Record<string, unknown>;
  expected?: unknown;
}
```

Кнопка «Сохранить как кейс» доступна во вкладке «Отладка». «Прогнать все»
последовательно вызывает `groovyExecutor.evaluate` и показывает
зелёный/красный статус (сравнение `output` с `expected`, deep-equal).
Кейсы с инлайн-Groovy в mock-режиме помечаются «не проверено», а не
«пройдено». `onChange` отдаёт кейсы вместе с `mappings`, чтобы платформа
их сохранила.

## 4. Подсказки по аргументам функций

### Что есть сейчас



- Обработчик получает `values: unknown[]`: позиционный список значений
  источников. Какое значение первое, определяется порядком соединения
  линий. Для `lineTotal = price × qty` это работает, для
  `buildAddress(customer, options)` — уже нет.
- `CustomHandlerDef` описывает только `appliesTo`, `minSources` и
  `maxSources`. Имён, типов и формы аргументов нет.
- Параметры (`HandlerParamDef`) — только примитивы (`string/number/boolean/
  select`). В UI это всегда текстовый `<input>`, поэтому число приходит
  строкой. Обработчики сейчас сами делают `Number(...)`, но это стоит
  исправить при переделке.
- Редактор инлайн-кода — голый `<textarea>` с подсказкой «`values` это
  массив значений источников». Автодополнения по структуре данных нет.
- Объект можно подключить как источник, но ни один обработчик, кроме
  `identity`, объекты не принимает, и нигде не видно, какую форму объекта
  обработчик ожидает.

### Как реализовать

**4.1. Сигнатура обработчика** — именованные типизированные аргументы
вместо `minSources/maxSources`:

```ts
interface ArgDef {
  name: string;                 // 'customer'
  label?: string;
  description?: string;
  type: FieldType;
  /** Для object/array — ожидаемая форма (тот же SchemaNode, что у деревьев). */
  shape?: SchemaNode;
  required?: boolean;
  variadic?: boolean;           // заменяет maxSources: Infinity
}

interface CustomHandlerDef {
  id: string;
  label: string;
  args: ArgDef[];
  returns?: { type: FieldType; shape?: SchemaNode };
  run: (args: Record<string, unknown>) => unknown;   // JS-двойник для превью
  groovy: string | ((args: Record<string, string>) => string);  // §1.2
}
```

`shape` удобно получать тем же `introspect()` из примера объекта, то есть
тем же подходом «схема из реальных данных», что уже используется для
source/target.

**4.2. Слоты аргументов в попапе.** Вместо списка «Источники (N)» —
именованные слоты с типами:

```
priceWithVat(
  price: number   ← $.cart[*].price    = 4990
  vatRate: number ← [не подключено] (по умолчанию 0.2)
) → number        = 5988
```

Источник перетаскивается в конкретный слот (`SourceRef.arg`, §2.1), и
позиционная зависимость от порядка соединения уходит.

**4.3. Объектные аргументы.** Для `type: 'object'` в слоте раскрывается
ожидаемая форма (`shape`) и проверяется совместимость с подключённым
источником (структурная проверка: обязательные ключи есть, типы
совпадают):

- ✓ `street: string` ← `$.address.street`
- ✗ `zip: number` — в источнике `string` (предложить `toNumber`)
- ⚠ `apartment` — нет в источнике

При несовпадении можно построить объект-аргумент прямо в слоте:
«вложенный мини-маппинг» с тем же UI деревьев. Структурно это
`FieldMapping` с `children`, как у перебора; в Groovy он генерируется как
map-литерал. Так пользователь передаёт объекты, не собирая их в коде.

**4.4. Подсказки в Groovy-редакторе.** `<textarea>` заменить на
CodeMirror 6 (есть режим Groovy, лёгкий) с собственным
completion-провайдером:

- автодополнение по структуре аргументов из `SchemaNode` подключённых
  источников: `args.customer.` → `name`, `address`, … с типами;
- сигнатуры встроенных и кастомных функций
  (`concat(values: List<String>, separator: String)`) с hover-описанием из
  `ArgDef.description`;
- при вводе `имяФункции(` — всплывающая подсказка параметров (signature
  help), как в IDE;
- доступные переменные процесса из `context` / вкладки «Отладка».

**4.5. Обратная совместимость.** Обработчики с `minSources/maxSources`
продолжают работать: адаптер строит `args` вида `[{ name: 'value0',
type: appliesTo[0] }, ...]` и превращает `Record` обратно в массив для
старого `run(values)`.
